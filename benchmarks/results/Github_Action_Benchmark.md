## 4. 方法学

- **构建**：`--release`，workspace `[profile.release]`（`opt-level=3`, `lto="thin"`, `codegen-units=1`）。
- **测量**：每个 case 先做时间有界的预热（至少 10 次迭代、再稳定 ~250ms，避免大 fixture 或慢 codec 的固定 500 次预热拖垮整轮），再按 `NEXTJSON_BENCH_MS`（默认 2000ms）时间窗计数 encode 与 decode 的 ops，取吞吐量（MB/s = ops × size / 1e6）与延迟（ns/op = 1e9 / ops）。
- **同一进程**：nextjson 与 serde 使用相同的 fixture、相同的预热与测量循环，直接可比。
- **全量矩阵**：每个数据形状 fixture 对所有能表示它的格式都做对比（JSON 三引擎 + MessagePack/CBOR/JSON5/YAML/RON/UBJSON/SMILE/NDJSON/TOML/BSON/postcard/bincode），不再是只对比 json/msgpack/cbor 三个格式。
- **数据形状**：9 个 fixture 覆盖混合记录、浮点密集、Unicode、纯整数、长文本、大数组、小对象、深层嵌套、文档形态，避免单 fixture 偏差。
- **nextjson `simd` feature**：本报告中的 nextjson 数字启用了 `simd`（x86-64：SSE2 基线 + AVX2 运行时检测；aarch64：NEON）。`simd` 是 opt-in 特性，默认构建保持 `#![deny(unsafe_code)]` 零 unsafe。
- **诚实声明**：
- `simd-json` 的 serde 解码要求可变输入缓冲（原地解析），因此其每次解码迭代包含一次 `to_vec()` 拷贝，该拷贝计入其耗时。
- serde_json 1.0.151 对 17 位有效数字浮点的解析有 1-ULP 误差（见第 2 节）；其 `numbers` fixture 的 self-check 使用 1-ULP 容差并如实报告。
- simd-json 的浮点序列化器对超出其格式化缓冲的极值（如次正规数 `5e-324`）报错，故 `numbers` fixture 的指数范围限定在 -6..+6。
- **UBJSON / SMILE 的 serde 侧缺口**：`serde_ubj` 0.2.0 的**解码器只支持有符号 32/64 位整数**（`u8/u16/u32/u64/i128` 全部返回 `Unsupported`），`serde-smile` 0.2.2 对 `u64` 的处理同样不完整（`id: u64` 等字段无法往返），而本报告的所有 typed fixture 都含无符号字段——因此这两个格式只呈现 nextjson 的完整 encode+decode 行，不呈现 serde 对比行；这是生态 crate 的真实能力限制，不是测量省略。nextjson 的 UBJSON/SMILE 字节级互操作（计数式/强类型容器、共享字符串/键名引用等）由 `formats_new` 集成测试按规范字节验证。
- 共享 CI 硬件的吞吐会随负载与散热漂移；本报告是单次运行的记录，不是严格的性能基准判决。
- `bincode` 无 nextjson 对应实现；TOML/BSON 需文档根、postcard 拒有符号标量，这三者使用 `config` fixture。
